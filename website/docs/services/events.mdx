# Events and workers

`@dotpress/events` lets your code announce what happened, and lets other code react to it, later, in workers. A route that places an order emits `order.placed` and answers at once; the confirmation email and the warehouse notification run in a worker, retried on their own when they fail.

The code that emits never knows where the listeners run: in the same process during development, in a container reading Redis, or in a Lambda function reading SQS. Changing the transport changes one line.

## Concepts

| | Role | Where |
| --- | --- | --- |
| **Event** (`defineEvent`) | a fact, with a name and the schema of its payload | shared code |
| **Listener** (`defineListener`) | a reaction to an event, with a unique name | shared code |
| **Bus** (`createEventBus`) | validates the events emitted, sends one message per listener to its transport | the code that emits: API, scripts |
| **Transport** | sends the messages to a queue: memory, Redis, SQS, Postgres… | the configuration of the bus |
| **Worker** (`createWorker`) | runs the listeners of the messages it receives | a container, a Lambda function, `dotpress-events work` |

`emit()` sends **one message per listener**: each listener is retried on its own, and can even run on another platform.

`load` imports the code of a listener, the default export of its module, only in the worker: the API that emits only needs the names of the listeners, not their dependencies. Event names use letters, digits, `.`, `_`, `:` and `-`; a listener name is unique, and renaming it orphans the messages still in queues under the old name. A listener can also be written inline, with `handle`:

```ts twoslash
import { defineEvent, defineListener } from '@dotpress/events'
import { z } from 'zod'

declare const crm: { addContact(userId: string): Promise<void> }
// ---cut---
const userCreated = defineEvent({
  name: 'user.created',
  schema: z.object({ userId: z.string() }),
})

const syncCrm = defineListener(userCreated, {
  name: 'sync-crm',
  handle: async ({ payload, logger }) => {
    await crm.addContact(payload.userId)
    logger.info({ userId: payload.userId }, 'Contact added to the CRM')
  },
})
```

The listener receives the parsed `payload`, typed by the schema, and:

| Field | Content |
| --- | --- |
| `id` | the identifier of the message, the same for every attempt |
| `attempt` | the attempt number, from 1 |
| `emissionId`, `emittedAt` | the emission |
| `metadata` | the metadata of the emission: the `requestId` with the plugin |
| `logger` | the logger of the worker |
| `event`, `listener` | the names |

### Payloads

**Payloads travel as JSON.** The bus serializes the payload, then validates it with the schema: an invalid payload throws an `EventPayloadError` at `emit()`, not later in a worker. Dates travel as ISO strings: convert them in the schema (`z.coerce.date()`, `.transform()`) if listeners need `Date` objects. Workers validate the payload again, against the current schema: a message emitted by a previous version of your code is checked too.

:::warning Pass identifiers, not secrets
Messages are stored by queues, shown in their consoles and kept in dead-letter queues. Send `{ userId }`, never a password, a token or personal data the listener can load itself.
:::

### Retries and idempotency

**A listener throws to be retried.** The transport delivers the message again, then moves it to its dead-letter queue after its retry limit.

**Make listeners idempotent.** Queues deliver messages at least once: a message can run twice, after a timeout or a duplicate delivery. Use `id` to ignore duplicates (a unique constraint, an idempotency key sent to the API you call), or make running twice harmless. Some queues also ignore a message sent twice, by its `id` ([see each queue](/deployment/event-workers)), but not all of them, and not always: it is a bonus, not a guarantee.

## Emitting

```ts twoslash
import { createEventBus, createMemoryTransport, defineEvent } from '@dotpress/events'
import { z } from 'zod'

const invoicePaid = defineEvent({
  name: 'invoice.paid',
  schema: z.object({ invoiceId: z.string(), paidAt: z.iso.datetime() }),
})
const events = createEventBus({ transport: createMemoryTransport(), listeners: [] })
// ---cut---
await events.emit(
  invoicePaid,
  { invoiceId: 'F-1', paidAt: new Date().toISOString() },
  { delay: '1h', metadata: { source: 'payments' } } // optional
)
```

The payload is typed by the schema of the event. `delay`, a number of seconds or a [duration](/concepts/options#durations) like `'1h'`, postpones the listeners, within the limit of the transport. `emit()` returns the `emissionId`, and one `{ id, listener, transport }` per listener; an event without listeners is not sent.

:::warning Emit after the transaction commits
An event describes something that happened. Emitted inside a database transaction that rolls back, it describes something that did not. Commit first, then emit.
:::

### Send failures

When some messages cannot be sent (the queue is down), `emit()` throws an `EventEmitError`, which lists the `sent` and `failed` messages. `retry()` sends the failed messages again, with the same ids, delay and metadata; the sent ones are not sent again:

```ts twoslash
import { createEventBus, createMemoryTransport, defineEvent, EventEmitError } from '@dotpress/events'
import { z } from 'zod'

const invoicePaid = defineEvent({
  name: 'invoice.paid',
  schema: z.object({ invoiceId: z.string(), paidAt: z.iso.datetime() }),
})
const events = createEventBus({ transport: createMemoryTransport(), listeners: [] })
const payload = { invoiceId: 'F-1', paidAt: new Date().toISOString() }
// ---cut---
try {
  await events.emit(invoicePaid, payload)
} catch (error) {
  if (error instanceof EventEmitError) await error.retry()
  else throw error
}
```

A new failure throws a new `EventEmitError`, whose `sent` also lists the messages sent before, with its own `retry()`. The error does not expose the payload: it can be logged as is.

A queue that cannot be reached does not always fail at once: a client may wait for the connection to come back. `emit()` waits 10 seconds at most for each transport (`sendTimeout` of `createEventBus()`, `false` for no limit); the messages of a transport that did not answer fail with an `EventSendTimeoutError`. A send given up this way may still complete later: `retry()` sends the same message ids, and listeners ignore duplicates by `id`.

### Emitting again: `emissionId`

`retry()` only works in the process that emitted. Each call to `emit()` is a new emission, with new message ids: emitting again later (a job that replays an outbox, a webhook received twice) runs again the listeners whose message was already sent. To avoid that, pass an `emissionId`, the idempotency key of the emission. The message ids derive from it: the same `emissionId` gives the same ids, and listeners ignore the duplicates by `id`.

```ts twoslash
import { createEventBus, createMemoryTransport, defineEvent } from '@dotpress/events'
import { z } from 'zod'

const invoicePaid = defineEvent({
  name: 'invoice.paid',
  schema: z.object({ invoiceId: z.string(), paidAt: z.iso.datetime() }),
})
const events = createEventBus({ transport: createMemoryTransport(), listeners: [] })
const invoice = { id: 'F-1', paidAt: new Date().toISOString() }
// ---cut---
await events.emit(
  invoicePaid,
  { invoiceId: invoice.id, paidAt: invoice.paidAt },
  { emissionId: `invoice-paid:${invoice.id}` }
)
```

**The `emissionId` names one occurrence of the fact, not its entity.** An invoice is paid once: `invoice-paid:${invoice.id}` fits. An order is updated many times: `order-updated:${order.id}` would make every update a duplicate of the first one; use `${order.id}:${order.version}`, or the id of an outbox row. It has 1 to 200 characters, without control characters. Only the ids are stable: `emittedAt` is the date of each call.

Without `emissionId`, make listeners idempotent on the data they change (a unique constraint on the order, an idempotency key derived from it), not only on the message `id`.

## In a route

```ts
import { eventsPlugin } from '@dotpress/events/plugin'

const app = await createApp({ adapter, plugins: [eventsPlugin(events)] })

defineRoute({
  method: 'post',
  path: '/orders',
  handler: async ({ req, events }) => {
    const order = await orders.place(req.body)
    await events.emit(orderPlaced, { orderId: order.id, items: order.items })
    return order
  },
})
```

`ctx.events` logs with the request logger, and adds the `requestId` to the metadata of the events: the logs of the listeners link back to the request. Using `ctx.events` without the plugin throws an explicit error. Outside a route, `events.withContext({ logger, metadata })` does the same.

## Transports

| Transport | Import | Use |
| --- | --- | --- |
| `createSyncTransport()` | `@dotpress/events` | runs the listeners inside `emit()`. Development, tests, apps without a queue |
| `createMemoryTransport()` | `@dotpress/events` | an in-process queue with retries. Development and tests: messages are lost when the process stops |
| `createBullmqTransport()` | `@dotpress/events/bullmq` | Redis, through BullMQ |
| `createSqsTransport()` | `@dotpress/events/aws-sqs` | Amazon SQS, with Lambda workers |
| `createPgBossTransport()` | `@dotpress/events/pg-boss` | Postgres, through pg-boss: no other infrastructure than your database |
| `createCloudflareQueueTransport()` | `@dotpress/events/cloudflare-queues` | Cloudflare Queues |
| `createPubSubTransport()` | `@dotpress/events/google-pubsub` | Google Cloud Pub/Sub |
| `createServiceBusTransport()` | `@dotpress/events/azure-service-bus` | Azure Service Bus |

The example picks its transport from the configuration: BullMQ with Redis, an in-memory queue in the API process without it.

```ts file="<root>/../examples/events/src/bus.ts"
```

Several transports can be used together: name them in the bus with `transports: { default, … }`, and route an event, or a single listener, with its `transport` option. Declare the names in the `EventTransports` interface to type-check them; the bus checks at startup that every listener has its transport. The setup of each platform (queues, dead letters, Lambda, containers) is described in [Event workers](/deployment/event-workers).

## Workers

A worker runs the listeners of the messages it receives. During development, run it next to your API with `dotpress-events work`:

```sh
npx dotpress-events work src/worker.ts --watch
```

The module exports the `worker`, the `source` of the messages, and optionally a `logger`:

```ts file="<root>/../examples/events/src/worker.ts"
```

Ctrl+C or `SIGTERM` stops the worker after the messages in progress; a second signal, a second later or more, exits at once. In production, the same command is the entry point of a container; on AWS Lambda, the SQS handler replaces it. See [Event workers](/deployment/event-workers).

## Failures

| Failure | What happens |
| --- | --- |
| The listener throws | the message is retried, then moved to the dead-letter queue after the retry limit |
| Invalid payload, unknown listener | retrying would not help: the message goes to the dead-letter queue at once when the transport can, or fails until the retry limit |

`onFailure(error, { envelope, attempt, final, reason })`, an option of the worker, is called for every failure: use it for alerts. Set `maxAttempts` to the retry limit of the queue, so that the last attempt is reported as `final`. An `unknown-listener` failure usually means a deployment mistake: a listener routed to a queue whose workers do not run it.

The options, the failure reasons, the logs and the errors are listed in the [Events reference](/reference/events).

## Testing

The memory transport runs the listeners in the test, and `drain()` waits for them:

```ts
const transport = createMemoryTransport({ retryDelay: () => 0 })
const events = createEventBus({ transport, listeners })

await placeOrder(events, order)
await transport.drain()
expect(transport.sent).toMatchObject([{ event: 'order.placed', listener: 'notify-warehouse' }])
```

To test the code that emits without running the listeners, use `createFakeEventBus()` and `expectEventEmitted()` of `@dotpress/testing`:

```ts
const events = createFakeEventBus()
await placeOrder(events, order)
expectEventEmitted(events, orderPlaced, { orderId: order.id })
```
